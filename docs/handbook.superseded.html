This handbook records not just what was built but why each significant decision went the way it did — particularly the ones about money, permissions and privacy, where the reasoning is the part that is expensive to reconstruct later.

How to read the boxes

Why boxes explain a decision that had a real alternative. Careful boxes flag something that will bite if forgotten. Gap boxes are things deliberately not built.

1 · What Deck is

Deck is a place where makers launch new tech — AI models, tools, Claude skills, mobile apps, websites, hardware — and the community votes, comments and reviews. A leaderboard resets every UTC day, so each launch gets its own day in front of people.

Four things were built on top of that core, in order:

  • A shop. Deck sells its own merch, and any maker can list theirs alongside it, subject to review.
  • A fundraise. Any launch can opt in to accepting contributions, with a target and a progress bar.
  • An ad service. Makers buy placements to promote their own launches, with Google AdSense filling unsold slots.
  • A back office. One gated admin area covering review queues, fulfilment, disbursements, roles and an append-only audit trail.

The rule that shaped everything

The original brief was explicit: no Redis, Kafka, RabbitMQ, Docker, Kubernetes, microservices, Prisma, PostgreSQL, GraphQL, event sourcing, CQRS or AWS-specific work. Keep the stack lightweight and focused on shipping.

That held throughout. The backend still has nine runtime dependencies. Several designs in this document — the derived ledger, the client-rendered share card, the SVG embed badge — are the direct result of solving a problem without reaching for a new service.

2 · Architecture

Two packages in one repository, deployable together or apart.

Frontend

React 19, Vite, TypeScript, React Router 7, TanStack Query 5, Tailwind CSS 4, Axios. A single-page app; all state that matters lives on the server.

Backend

Express 4, TypeScript, Mongoose 8, Zod for validation, JWT with bcrypt for auth, Multer for uploads. No ORM beyond Mongoose, no job queue, no cache layer.

Request shape

Every response is { success, data } or { success, error }, with paginated lists adding a meta block. Errors are thrown as ApiError and caught by one handler, so a controller never assembles an error response by hand.

Validation is Zod at the route boundary via a validate middleware. By the time a controller runs, its input is typed and trusted.

Serving

In development Vite serves the app and proxies /api. In production the backend can serve the built frontend itself, which is what makes per-launch link previews possible (§11). It detects a build and stays out of the way when there isn't one, so running the API headless is unaffected.

3 · The design system

Neo-Brutalist Pop: flat colour, 2px borders, hard offset shadows with no blur or alpha, Archivo Black for display, Geist for body, Geist Mono for anything that reads as a machine value. Motion is fast and mechanical — things snap rather than glide.

Themed tokens

Dark mode is not a set of dark: overrides. Six semantic CSS variables are redefined under .dark and exposed to Tailwind as colours: 

--canvas  --surface  --surface-2  --edge  --body-ink  --muted-ink

A component writes border-edge once and it flips. The hard shadows reference var(--edge) too, so they invert with everything else.

Why — errors have no colour

Anything destructive or wrong is shown by inversion — bg-edge with text-canvas — rather than a warning hue. Because those two tokens swap between themes, it reads black-on-white in light mode and white-on-black in dark. Unmistakable, and it costs no extra colour.

The palette

The two accents are a pair, not two picks

Lime sits at luminance 0.82 and slate at 0.06, near opposite ends of the scale. That is the whole design: each carries the other's text at 8.1:1, in both directions, so a block can be bright with dark type or the same block inverted. Hierarchy comes out of the pairing, which is why no third hue is needed. It also survives greyscale printing, which the previous pair did not.

Careful — blocks are fixed, marks are themed

lime and slate are identical in both themes because they are block fills: a filled panel brings its own background and its own text, so it does not care what the page behind it is doing. A new bg-lime surface must carry text-slate, and a new bg-slate surface must carry text-lime. text-ink on slate is 1.9:1.

Anything that sits on the page instead — link text, a focus ring, a 1px rule, a progress fill, an SVG stroke — must use accent, which is themed. This is not a preference: no fixed colour can clear 4.5:1 against both #FAF9F5 and #151515, because light demands a luminance under 0.17 and dark demands over 0.20. Reaching for text-lime on the light canvas gives 1.15:1.

The same split governs detail drawn inside a block. Illustration marks and mascot eyes take the partner colour rather than --edge, since --edge flips with the theme while the block does not — an edge-coloured mark inside a block is guaranteed to vanish in one theme or the other.

The mascots

Two draggable characters flank the hero. The eyes are treated as patches on the surface of an implied sphere, projected each frame — which is what makes them slide toward the silhouette and compress as the head turns, rather than just sliding around a flat face. A sphere's outline doesn't change when it rotates, so the oval holds still while the eyes move across it.

They track the cursor on all three axes: direction for x and y, and proximity for z, which makes them lean in and widen their eyes as you approach. When the cursor is far away they turn to look at each other. Every frame is written straight to the DOM from a rAF loop — a setState per mousemove would re-render the hero sixty times a second for an animation React has no opinion about. Both respect prefers-reduced-motion and are hidden from assistive tech.

4 · Data model

UserAccount, profile, role: user | admin

PayoutA disbursement Deck has sent a seller
AdCampaignA paid placement, its creative, window and counters
BadgeAwardA badge somebody has earned, with the date
AuditEventOne privileged action. Append-only

Money is always integer minor units

Kobo for NGN, cents for USD — everywhere, end to end. Floats cannot represent 0.1 exactly, so a cart of three items at 19.99 would drift. It is also exactly the unit Paystack expects, so nothing is converted at the boundary. The client never sees or sends a decimal price; formatMoney on the frontend is the single place a decimal appears.

Why — stored versus derived

The codebase makes this choice differently in two places, on purpose.

A seller's balance is derived — earnings minus payouts, recomputed on every read. It costs an aggregation and buys a number that cannot silently drift. A stored balance goes wrong the first time an increment fails after its transaction committed, and on a ledger nobody external reconciles, nothing would notice.

A badge is stored. An achievement is a fact about the past: you did top the board. If that launch is deleted next year, a derived badge would quietly take it back.

5 · Launches, votes and the board

Anyone signed in can submit a launch: name, tagline, description, category, tags, pricing model, links, logo, cover and gallery. Uploads are verified by magic bytes rather than by the declared MIME type, given a server-generated filename, and served with X-Content-Type-Options: nosniff. SVG is not accepted.

Votes are one per person per launch, toggled. Comments are threaded, and a top-level comment can carry a rating, which feeds the launch's average.

The daily board ranks by votes within one UTC day. launchDateKey is denormalised onto every launch as YYYY-MM-DD, so a day's board is an indexed lookup rather than a date-range scan. Weekly, monthly, yearly and all-time boards exist on the backend.

6 · The shop

Deck's own catalogue and maker-listed products share one shelf. A listing is buyable only when two separate switches agree: Deck has approved it, and the seller has it switched on. Every public read goes through one filter constant, so a product can never appear in one place while being hidden in another.

The review queue

Anything a maker lists arrives pending and reaches the shop only once staff approve it. Rejection requires a reason, which the seller sees on their own shop page — a listing that silently fails gives them nothing to fix.

Why — editing sends a listing back for review

A seller editing an approved listing returns it to the queue. Otherwise approval is a one-time gate: get a plain tote through, then rewrite it into anything you like. The listing form says so rather than letting a seller discover it when their product vanishes.

Stock and checkout

The checkout payload carries SKUs and quantities only — deliberately no prices. Every line is priced from the database. A tampered cart can change what is ordered, never what it costs.

Stock is reserved with a conditional update per line ($elemMatch requiring stock ≥ n), so two people buying the last item cannot both win. If any line loses the race, everything already reserved is handed back and the order row is deleted — releasing stock alone would leave an unpayable order sitting in the customer's history.

Careful — the merged-quantity cap

Zod enforces the per-line quantity limit, which on its own is bypassable by sending the same SKU twice: ten plus ten arrives as two valid lines. Duplicate SKUs are collapsed first and the cap is re-checked against the merged total.

7 · How money moves

Every payment — merch, contributions, ads — is a Paystack transaction that settles into Deck's own account. Deck then owes sellers their share and disburses it periodically. Two rules govern the integration:

  1. The secret key never leaves the server. The browser only ever gets an authorization URL.
  2. Nothing is ever marked paid because the browser came back from checkout. The customer controls that redirect. Payment is confirmed only by asking Paystack directly, or by a signature-verified webhook.

The webhook

Paystack signs the raw request body with HMAC SHA-512. The webhook route is mounted before express.json() — once that has parsed and discarded the buffer, the signature can never be recomputed. Comparison is timingSafeEqual, length-guarded because it throws on a mismatch.

Careful — do not move the webhook route

Registering it after the JSON body parser silently breaks signature verification. Every webhook would then be rejected as forged, and payments would only ever settle via the browser callback.

Idempotency

The callback and the webhook both arrive for every transaction, and webhooks retry for days. Each settlement path is guarded on its pending state, so a single contribution cannot land on a progress bar twice, and a seven-day ad campaign cannot start twice.

Every settlement also re-checks that the amount and currency Paystack confirmed match what was asked for. A mismatch means the transaction was tampered with or belongs to something else, and is never treated as payment.

The ledger

A seller's balance is earned − paid out, computed from the source rows on every read. Only settled money counts: an abandoned checkout owes nobody anything.

Each order freezes a per-seller settlement share at checkout:

netMinor = goodsMinor − platformFeeMinor + shippingMinor

The fee percentage can change next week; what a seller earned on this sale cannot.

Shipping goes to the seller

Whoever posts the parcel gets the postage, allocated across a mixed basket in proportion to goods value. Allocation uses a largest-remainder helper so the parts sum to exactly what the buyer paid.

Why — rounding each share separately is a bug

Round each seller's share independently and a kobo goes missing on most orders. Over thousands of orders that is a ledger which never balances and nobody can explain. allocate() floors every share, then hands the leftover units to whoever lost most to rounding — ties breaking toward the earlier entry, so the same input always gives the same output.

The platform fee applies to goods only. Shipping is a pass-through; commission on postage would mean Deck earning from the courier.

Disbursement

Staff see everyone owed, largest first, send the transfer from the bank, and record it. Recording more than the outstanding balance is refused, not clamped — an overpayment is almost always a typo, and a ledger that quietly accepts one stops meaning anything.

Gap — where to send the money

Payout accounts were removed when the architecture moved to central collection. Nothing in the app records a seller's bank details. The disbursement form has a free-text “sent to” field for tracing after the fact, but you will be collecting those details by email or DM until that changes.

8 · Fundraising

Any launch can opt in — never opt out, and never implied. The launcher sets a target and a pitch; backers give from ₦1,000 up, optionally with a message and optionally anonymously. The owner sees settings where everyone else sees the progress bar.

Keep what you raise. A confirmed contribution is final and missing the target costs nothing. There is no pledge state and no deadline, which is why the running total can be incremented on confirmation and trusted from then on.

Guards, all enforced server-side:

  • The amount is priced and split on the server; the client sends a figure and nothing else.
  • You cannot back your own launch.
  • Below the floor or above the ceiling is refused.
  • A raise that is disabled or closed takes nothing.
  • Turning a raise off stops new money but leaves the history and total alone — what was given was given, and hiding it would misstate the record.

The progress bar caps at 100% so it cannot overflow, while the figures beneath it tell the truth about an over-funded raise.

9 · Advertising

Makers buy a slot on Home, Discover or the daily board for 7, 14 or 30 days. The price is derived on the server from a rate card; the payload carries no price.

Why — review happens before payment

Charging first would mean owing a refund every time an ad is turned down, and Deck has no refund flow. The order of those two steps is the difference between a rejection being a non-event and being a support ticket about somebody's money.

Two things an advertiser deliberately cannot set:

  • The destination. A paid slot redirecting wherever the caller asked would be an open redirect carrying Deck's endorsement. The link comes from the campaign's own launch, server-side.
  • Markup. The creative is stored as fields and rendered in Deck's styling, so an ad cannot run a script, restyle the page, or pass itself off as editorial. It is labelled and dashed-bordered, and the label is not optional.

Rotation is least-served-first, so delivery stays even over a short run. Scheduled, running and finished are derived from the window rather than stored — a stored copy would need a job to stay honest.

Google AdSense

A slot shows the paid Deck ad, else a Google unit, else nothing. The fallback chain lives in one component, so pages only declare where a slot is.

Nothing loads before consent. The tag is injected on demand rather than sitting in index.html, which would hit googlesyndication.com on every page load, for every visitor, before anyone agreed — and on pages with no ad slot at all.

StateThird-party requests
0No publisher ID configured — and no banner, since there is nothing to ask about
0Configured, reader has not answered
0Reader declined
✓Reader allowed — tag loads, unit renders, labelled

An unanswered banner is treated exactly as a decline, and a localStorage failure fails closed. The two buttons differ only in which is filled — a decline hidden behind a settings page is the pattern regulators call a dark pattern.

Gap — this is not a certified CMP

The gate is honest and it works, but if you take meaningful EEA/UK traffic, Google requires a Google-certified consent platform for personalised ads. Worth resolving before switching AdSense on.

10 · Badges

Fifteen badges across three families — making, community and trade — so the set rewards more than shipping. A board that only celebrates launches tells everyone who votes and comments that they are furniture.

The evaluator runs after votes, comments, launches and settled payments, and again on profile view as a backstop — so a missed hook, or one added later, resolves the first time anyone looks. It never throws: a badge that failed to save is not a reason to fail the vote, and the next evaluation picks it up. A unique index absorbs concurrent evaluations racing on the same milestone.

The trophy case shows unearned badges too, with progress. That is the difference between “locked” and “two more to go”.

Careful — a bug worth remembering

Board-finish badges silently read zero for someone who had clearly topped a board. launchDateKey was missing from the query projection, so the ranking aggregation matched [undefined] and found no days at all — making every board badge unwinnable, with no error anywhere. Found by checking the metric against the raw board data rather than trusting it. Keep that field in the projection.

11 · The share kit

Three artefacts, because it is three different jobs.

A downloadable card

1200×600 PNG, rendered client-side in canvas. Not server-side, and for a specific reason: the browser already has Archivo Black and Geist loaded. A server renderer would need those fonts installed beside it and would silently fall back to something generic the day a deploy forgot them — producing an off-brand brand card with nothing to alert anyone.

An embed badge

SVG, served from /api/share/:slug/badge.svg, cached an hour with stale-while-revalidate. SVG because it is fetched on every view of every page that embeds it, so it needs to be tiny and stay crisp. Supports a dark variant and a plain style. Shown live in the panel from the same URL the snippet uses, so what you copy is provably what you saw.

Link previews

Before this, every Deck link unfurled identically — share a launch anywhere and it showed “Deck” with Deck's generic blurb, because crawlers do not run the JavaScript that would fix it.

The backend now serves the built frontend with per-launch Open Graph tags injected, using the product's own cover art — already uploaded, already a raster, already the picture of the thing being shared. No image renderer needed. Relative paths are made absolute, and the card upgrades to summary_large_image only when there is an image worth showing large.

12 · The admin area

One gated area at /admin with six tabs. The shell itself is the guard, so any admin route added later is protected by existing under it — there is nothing to remember per page.

TabWhat it does
OverviewWork queues first, each one a person waiting. Tiles highlight only when they have work; badges appear only above zero
ReviewMerch queue, oldest first, full description shown. Approve is one click; reject demands a reason
OrdersFulfilment. Opens on paid-and-unposted, the only view with work in it
PayoutsThe disbursement run
AdsCampaign review — nothing here has been charged yet
PeopleSearch, filter by role, promote and demote
TrailThe audit log

Creating an admin

npm run create-admin -- --email you@example.com --name "Your Name"

Promotes an existing account, or creates one and prints a generated password once. --demote reverses it.

Why — a command, not an endpoint

Staff access hands over everything else: the catalogue, every order, the disbursement run, other people's roles. An HTTP route granting it is a route worth attacking, and the first admin has to come from somewhere that is not the internet. Running the command needs shell access to the server and database, which is the right bar.

The password is generated rather than passed as an argument — a --password flag would leave it in shell history and in ps.

Lockout guards

  • You cannot demote yourself. The easiest way to lock every admin function behind a door nobody can open, and always a misclick.
  • The last admin cannot be demoted, by the API or the CLI.

Order transitions

Forward only, one step at a time: paid → shipped → delivered. Skipping, repeating and moving from a terminal state are all refused.

Why — an admin cannot cancel a paid order

It implies a refund, which has to happen at the payment provider. Doing it here would leave the ledger claiming a seller earned money that went back to the buyer. Until refunds exist as a real flow, nobody can half-do one by accident.

13 · The audit trail

Thirteen privileged actions are recorded. Three properties make it a trail rather than a table.

Append-only, enforced at the schema

updateOne, updateMany, findOneAndUpdate, findOneAndReplace, replaceOne, deleteOne, deleteMany, findOneAndDelete and .save() on an existing document all throw. Putting the guard on the model rather than trusting callers means a future handler — or a careless script — cannot quietly rewrite history. There is no endpoint to amend it either.

Self-contained entries

Actor and target names are copied in, not joined. Normally a smell; here it is the point. An entry has to still read correctly in a year, after the admin has left and the product has been renamed. “Ada approved Jonas's Field Cap” survives that; two dangling ObjectIds do not. Each entry also carries before/after snapshots.

Logging cannot break the action

The recorder never throws. The action being logged has usually already happened — a role is changed, a parcel is posted, a bank transfer has left. Failing the request would roll back the API's view of something the real world already did, which is worse than a gap in the log. Failures are swallowed and shouted to stderr.

That reasoning only holds because no audited action's sole record is the audit entry — each also writes its own row. The entry corroborates; it is not the only evidence.

Ordinary work is deliberately excluded. A seller editing their own listing produces no entry; staff editing someone else's does. Logging everything would bury what matters.

14 · Security & integrity

The guards that were built deliberately, and verified by direct testing.

AreaGuard
AuthJWT, bcrypt-hashed passwords, requireAuth / requireAdmin middleware
PricingEvery price derived server-side. Merch, contributions and ads all ignore any client-sent amount
OwnershipListings, launches, orders, campaigns and contributions all check the caller owns the thing
PaymentsAmount and currency re-verified against the provider before anything settles
WebhooksHMAC SHA-512 over the raw body, timing-safe comparison, 401 on mismatch
UploadsMagic-byte sniffing, server-generated filenames, nosniff, no SVG
RedirectsAd destinations come from the campaign's own launch, never the request
InjectionAd and merch creatives are fields, not markup. Search patterns are regex-escaped
PrivacyNo third-party script loads without consent; unanswered is treated as declined
AuditAppend-only at the schema; role and money actions all recorded

Verified by testing, not assumed

Each of these was exercised against a running server and confirmed to behave:

  • Price tampering ignored; sold-out and over-stock rejected; cross-user order access forbidden.
  • Split maths exact on a mixed basket — fee + net = gross, shipping allocated in full, nothing lost to rounding.
  • Full ledger cycle: unpaid earns nothing → paid lands → part payout → settled clears the run.
  • All nine audit mutation paths refused; the entry survived unchanged.
  • Every admin route 403s a member and 401s a signed-out caller.
  • Self-demotion and last-admin demotion both refused, via API and CLI.
  • Order transitions: skipping, repeating and terminal moves all refused.
  • Ad lifecycle: pay-before-review refused, self-approval refused, expired and future windows serve nothing, rotation even at 4/4.
  • AdSense: zero third-party requests in all three non-consenting states.
Careful — the IP column

The audit trail records req.ip, which behind a reverse proxy is the proxy unless TRUST_PROXY is set. An IP column reading “the load balancer” on every row is worse than no column — it looks like evidence and is not. It is off by default because trusting X-Forwarded-For with no proxy in front lets any client claim any address.

16 · Known gaps

Things deliberately not built, in rough order of how much they matter.

  1. Email. No outbound mail at all — no receipts, no “your listing was approved”, no rejection notice, no payout confirmation. Sellers currently learn they were rejected by checking. This is the biggest hole in the product.
  2. Refunds. None. This constrains design everywhere money moves: it is why ads are reviewed before payment, and why an admin cannot cancel a paid order.
  3. Seller bank details. Nothing records where to send a disbursement (§7).
  4. A certified consent platform. Required by Google for personalised ads to EEA/UK traffic (§9).
  5. Impressions measure serves, not views. Fine for flat-rate billing where the number is informational; it would need to be far more defensible before it could price anything.
  6. No automated tests. Everything in §14 was verified by driving a running server, not by a suite that would catch a regression tomorrow.
  7. Comment moderation is reactive. An admin finds a bad comment by chance. Reports plus a queue would use the audit trail already in place.
  8. Live Paystack was never exercised. No key was available in the development environment. Every payment path is written to the API contract and verified up to the provider boundary, but no real transaction has been made. Get a test-mode key before this goes near real money.
Suggested next steps

Email first — it unblocks the seller and advertiser experience more than anything else on this list. Then a test-mode Paystack key to close the last unverified boundary. Then refunds, which several designs are currently working around.
